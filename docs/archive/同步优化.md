二、现状诊断
时间戳比对逻辑
核心逻辑位于 pullNewData 方法（InventoryRepositoryImpl.kt:511-590）和服务端 pull_data（record.py:~400）：

环节	逻辑	问题
存储	settingsRepository.getLastSyncTime(sessionId) 存在 Android 本地 DataStore	✅ 设计合理，替代了旧的 SharedPreferences
查询	服务端 last_update_time > lastSyncTime（严格大于）	⚠️ 边界：同一毫秒内的记录会被漏掉
更新锚点	取本批 maxServerTime，仅当 maxServerTime > currentSavedTime 时更新	⚠️ 无防倒退逻辑，如果服务端时钟回调，锚点会倒退
服务端时间	增量 push 时服务器强制覆写 last_update_time = int(time.time() * 1000)	❌ 严重：丢弃了客户端的原始修改时间，导致双向同步时间线失真
🔴 关键缺陷清单
1. 全量上传/下载的"先删后插"无事务保护

# record.py:77 - 全量上传
db.exec(delete(StockRecord).where(StockRecord.session_id == real_server_id))
# 如果下面的 insert 循环中发生异常，数据已丢失，无法回滚
for r in data.records:
...
Android 端同样（InventoryRepositoryImpl.kt:482），deleteRecordsBySession 和后续逐条 insert 不在事务中。

2. 增量上传成功后误标记全部脏数据为已同步

// InventoryRepositoryImpl.kt:393
val successIds = dirtyRecords.map { it.id }
stockRecordDao.markAsSynced(successIds)
即使服务端只处理了部分记录（例如中途崩溃），Android 端也会把所有脏记录标记为已同步，导致数据丢失。

3. 增量下载的时间戳锚点可能漏数据

# record.py - 严格大于，同一毫秒的记录可能被跳过
StockRecord.last_update_time > lastSyncTime
高并发场景下（如批量扫描），同一毫秒内可能产生多条记录，> 会导致边界遗漏。

4. 无冲突检测机制

增量下载（pullNewData）直接用服务器数据覆盖本地（OnConflict.REPLACE），如果用户在离线期间修改了同一记录，本地修改会被静默覆盖。
syncStatus = 1 的本地修改会在 copy(remote, ...) 时被覆盖为 0，丢失 dirty flag。
5. 产品数据同步不一致

同步路径	产品数据行为
全量上传	✅ 上传并更新服务端产品
增量上传	⚠️ 上传产品但服务端只更新部分字段
全量下载	❌ 只插入新产品，不更新已有产品
增量下载	❌ 完全不处理产品数据
6. 无网络重试机制

所有同步方法都是单次 try-catch，局域网断开时直接 Result.failure，没有任何重试或退避策略。

7. 并发/竞态

SyncViewModel.isSyncRunning 只能防止同时启动两次同步，但不能防止用户在同步中途修改数据（例如扫码新增记录）。
服务端无任何乐观锁或版本号校验，两个客户端同时 push 会互相覆盖。
8. 服务端 db.commit() 分散调用

增量 push (record.py) 中，db.commit() 被执行了 3 次（产品提交、可能的 session 创建提交、记录提交），中间任何一步失败都会导致数据部分写入。

三、重构方案大纲
总体原则
不推翻现有业务逻辑，通过 Strategy Pattern 解耦四种同步操作、统一时间戳管理器、引入重试/退避机制 三层递进式重构。

第一层：策略模式解耦四种同步操作
目标：将 InventoryRepositoryImpl 中互相缠绕的四个同步方法（600+ 行单一文件）拆为独立策略。

data/sync/
├── SyncStrategy.kt              # 策略接口
├── FullUploadStrategy.kt        # 全量上传
├── IncrementalUploadStrategy.kt # 增量上传
├── FullDownloadStrategy.kt      # 全量下载
├── IncrementalDownloadStrategy.kt # 增量下载
├── SyncOrchestrator.kt          # 同步协调器（替代 ViewModel 中的分散调用）
└── SyncContext.kt               # 同步上下文（携带 IP、sessionId、回调等）
接口定义：

interface SyncStrategy {
suspend fun execute(context: SyncContext): SyncResult
}
SyncOrchestrator 职责：串行化同步请求（替代 isSyncRunning 简陋锁）、维护全局同步队列、在四种策略之间协调产品数据的统一同步、提供进度回调。

变更范围：

InventoryRepositoryImpl 不再直接持有同步逻辑，改为委托给 SyncOrchestrator
SyncViewModel 直接与 SyncOrchestrator 交互，不再直接调 Repository 的 sync 方法
第二层：统一时间戳管理器
目标：解决当前时间戳逻辑分散、边界遗漏、时钟偏差三大问题。

data/sync/
└── TimestampManager.kt          # 时间戳统一管理（新增）
核心设计：

改进点	当前	重构后
锚点存储粒度	每个 session 一个 lastSyncTime	每个 session 保存 {lastPullAnchor, lastPushAnchor} 两个独立锚点，pull 和 push 互不干扰
边界条件	> 严格大于	改为 >= 配合去重逻辑，避免毫秒级遗漏

产品时间戳	产品无时间戳追踪	给 ProductBase 增加 lastUpdateTime 字段，增量同步时一并拉取

StockRecord.last_update_time 不再被服务端覆写，改为 last_server_sync_time，保留原始 client_update_time
增量 pull API 的 SQL 查询改为 MAX(last_update_time, last_server_sync_time) >= :anchor
第三层：局域网超时重试与事务安全
3.1 重试机制（Android 端新增 RetryPolicy）

data/sync/
└── RetryPolicy.kt               # 重试策略
参数	默认值	说明
maxRetries	3	最大重试次数
baseDelayMs	500	初始退避延迟
maxDelayMs	5000	最大退避延迟
backoffMultiplier	2.0	指数退避因子
retryableExceptions	SocketTimeoutException, ConnectException, UnknownHostException	仅网络异常重试，业务错误不重试
class RetryPolicy(...) {
suspend fun <T> execute(block: suspend () -> T): Result<T> {
var attempt = 0
var delay = baseDelayMs
while (true) {
try {
return Result.success(block())
} catch (e: Exception) {
if (++attempt >= maxRetries || !isRetryable(e)) {
return Result.failure(e)
}
delay(delay)
delay = (delay * backoffMultiplier).toLong().coerceAtMost(maxDelayMs)
}
}
}
}
每个 Strategy 在发出 HTTP 请求时包裹 RetryPolicy。
