# QR码与单据校验逻辑审查

## 校验架构概览

校验涉及**两层**：底层 GS1 条码解析 + 上层业务单据匹配。

---

## 1. GS1 条码解析 (`Gs1Parser.kt`)

`Gs1Parser.parse()` 是所有校验的入口。它将原始扫描字符串解析为 AI（应用标识符）键值对：

- **AI `01`** → `di`（GTIN/DI，产品标识，定长 14 位）
- **AI `10`** → `batch`（批号，变长最多 20 位）
- **AI `17`** → `expiry`（效期，定长 6 位）
- **AI `11`** → 生产日期，**AI `21`** → 序列号 等

**解析有效性判断** (`Gs1Parser.kt:110`)：至少解析出 `01`（DI）才算有效 UDI 码。

---

## 2. 批量扫码模式 — `BatchScannerViewModel.assignStatusToBarcodes()` (`BatchScannerViewModel.kt:204`)

这是**图片批量识别**后的校验逻辑：

```
流程图：
条码识别 → Gs1Parser.parse() → 提取 "DI|批号" key → 与单据池匹配 → 消耗额度
```

### 模式 A — 无单据 (`targets == null`)

所有扫出的码直接标记为 `MATCHED`（绿框）。

### 模式 B — 有单据 (`targets != null`)

1. 每个条码解析出 `DI` + `批号`，拼接为 `"DI|批号"` 作为匹配 key
2. 在 `remainingTargets` 列表中查找该 key
3. 找到 → 标记 `MATCHED`，**从池中移除该 key**（消耗额度，防止重复匹配）
4. 未找到 → 标记 `MISMATCHED`（红框）

**关键问题**：匹配是全等对比（`it == key`），任何微小差异（大小写、空格）都会导致 MISMATCHED。没有模糊匹配容错。

## 3. 主界面扫码模式 — `InventoryMainViewModel.processScannerResults()` (`InventoryMainViewModel.kt:87`)

这是**单码扫码/连续扫码**后的校验逻辑，比批量模式更复杂：

```
条码 → Gs1Parser.parse() → DI + 批号 → 产品库查询 → 单据核对 → 贪心分配
```

### 校验步骤

**Step 1 — 格式校验** (line 111)：
无法解析或 `isUdi == false` 或 `di == null` → 标记 `isError=true`，"非 UDI 格式"

**Step 2 — 产品库查询** (line 128-130)：
`product = repository.getProductByKey(di)` — 查不到则产品名标记为 "未知商品"

**Step 3 — 单据核对** (line 99-104, 133-135)：
根据 `docDiBatchSet`（从 `_recordList` 中提取的 `(DI, 批号)` 集合）判断当前扫描结果是否在单据中：
- `inDocument == false` → `isError=true`，"不在单据中"
- `inDocument == true` → 继续

**Step 4 — 贪心分配** (line 148-168)：
对匹配同一 `(DI, 批号)` 的记录：
1. 找第一个 `actualQty < targetQty`（还没装满）的记录，`actualQty += 1`
2. 如果所有匹配记录都装满了 → 溢出到最后一条，状态自动变为 `OVERFLOW`
3. 如果找不到任何匹配记录 → 创建 `isError=true` 的记录，`documentId="UNKNOWN"`

## 4. 单据导入时的校验 (`InventoryMainViewModel.kt:253,299`)

### JSON 文件导入 (`importTargetDocumentFromJson`, line 253)

- 解析 JSON → `TargetDocument`（含 `items: List<TargetItem>`）
- 每个 `TargetItem` 包含 `materialCode`、`productName`、`batch`、`targetQty` 等
- `materialCode` 通过 `repository.getProductByMaterialCode()` 反查本地 DI — **这里没有校验物料编码是否存在**，查不到就 `di = ""`，后续所有匹配都会失败。

### 局域网批量拉取 (`loadMultipleTaskDetails`, line 299)

- 从 Python 服务端逐个拉取 `fetchPythonTaskDetail(id)`
- 同样的物料编码 → DI 映射逻辑
- **加载成功后直接覆盖**现有的 `_photoList`、`_photoScanResults`、`_currentDocuments`、`_recordList`

## 潜在问题总结

| 问题 | 位置 | 说明 |
|------|------|------|
| 物料编码无校验 | `InventoryMainViewModel.kt:271` | `getProductByMaterialCode()` 返回 null 时 `di=""`，后续全部匹配失败 |
| 批号全等匹配无容错 | `BatchScannerViewModel.kt:219` | 大小写差异、前后空格会导致误判 MISMATCHED |
| `InventoryRecord` 导入未同步 `documentId`/`documentName` | `importTargetDocumentFromJson:281` | 单文件导入时生成的 `InventoryRecord` 没有填入 `documentId`/`documentName`，而 `loadMultipleTaskDetails` 有填 |
| 单据 DI 集合只从已扫描记录构建 | `processScannerResults:99-103` | 如果 `_recordList` 初始为空（actualQty 都为 0），第一次扫描会找不到任何匹配，直接判定为 "不在单据中" |
| 网络任务列表过滤条件 | `InventoryMainViewModel.kt:51` | `status == 0`（未完成），如果服务端状态定义不一致会漏掉任务 |
