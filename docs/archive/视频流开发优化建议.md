无序列码 (21) 时，工业级 2D 视频流如何去重？

既然条码文本一模一样，且没有 3D 空间坐标，2D 视频流要实现去重，必须依赖 “2D 帧间追踪（Tracking）” 或 “交互规约（Workflow）”。

方案 1：基于 IoU（交并比）的 2D 矩形框轨迹追踪

不能用条码文本做 Key，但可以利用 “物理位置的连续渐变”。

原理： 相机帧率通常是 30fps，手机移动时，同一个盒子在第 1 帧和第 2 帧的 x, y 像素坐标变化极其微小。

做法：

第 1 帧扫到框 A（坐标 [100, 100, 200, 200]），生成临时 ID：Track_1，计数 +1。

第 2 帧扫到框 B（坐标 [105, 102, 205, 202]），计算框 A 与框 B 的重叠面积占比（IoU）。

如果重叠率 > 50\%，判定 B 就是上一帧的 A，将 Track_1 的坐标更新为 B，不追加计数。

只有当画面中出现了一个全新的框，且与当前所有正在追踪的 Track 重叠率都几乎为 0 时，才生成 Track_2，计数 +1。

方案 2：准星/检测线触发（ROI Gate）

这是大部分仓储扫描枪和工业 PDA 最推荐的非序列号扫掠方案。

原理： 放弃“全屏盲扫”，在屏幕中央设定一个透明的 “扫描闸门”（比如一条亮颜色的横线或矩形框）。

逻辑：

画面边缘看到的条码只画黄色框（提醒用户看到了），不记账。

只有当条码的中心点划过/穿过中央准星线的瞬间，触发一次闪绿光，计数 +1，并进入 1~1.5 秒的短时间冷却（防止手抖回弹）。

操作感： 用户拿着手机从上往下顺畅地“刷”过那一排试剂盒，每划过一个盒子就响一声/绿一下，既不会重复，也不会漏扫。

人在扫码时，会有手抖（原位震荡）、停顿（悬停）、猛刷（快速移动），甚至倒退（扫错了退回来）。如果仅仅依靠时间冷却或者简单的两点距离，系统绝对会崩溃。

大厂（如顺丰、京东物流的自研手持终端软件，或是商业级的 Scandit）在面对没有序列号、长得一模一样的货物时，从来不会单纯依赖底层 AI 算法去“硬抗”。他们的核心策略是：用“空间状态机（State Machine）”配合“强视觉交互”，把不确定的物理动作变成确定的逻辑事件。

既然你的 BatchScanner 是自己掌控底层的帧处理逻辑，以下是工业级 APP 解决“快慢、停顿、倒退”问题的标准打法，不需要复杂的深度学习追踪算法，非常适合在现有的架构上落地。

工业级解法：地铁闸机模型（方向性越线检测）

大厂不会只画一条线然后看“有没有碰到”，而是把这条线做成一个带有方向的“虚拟闸机”。

在你的 VideoStreamViewModel 接收每一帧数据时，为每一个正在视野里的条码维护一个极其简单的状态：

1. 解决“停顿与手抖”：状态锁定

痛点：用户把条码停在线上，手轻微抖动，导致条码中心点在准星线上下反复横跳，瞬间计数 +10。

大厂方案：引入状态机。

一个盒子从屏幕上方进入，状态是 APPROACHING（接近中）。

当条码中心点首次跨过准星线，触发计数 +1，状态立刻锁定为 COUNTED（已计数）。

关键点：只要这个条码还在屏幕视野内（哪怕它在线上疯狂抖动、停顿 1 分钟），只要它的状态是 COUNTED，就绝对不再触发计数。

2. 解决“倒退与反扫”：方向向量 (Y轴位移)

痛点：用户从上往下扫了 3 个，突然觉得没看清，把手往回（从下往上）退了一下，系统又把刚刚的盒子算了一遍。

大厂方案：只认单向。

记录上一帧的 Y 坐标和当前帧的 Y 坐标。

只有当 Y_{current} > Y_{previous} （假设是从上往下扫），并且跨过了准星线，才算有效越线。

如果是倒退扫（往回拉），直接忽略。

3. 解决“快一点慢一点”：帧间跳跃检测

痛点：用户手速太快，第 1 帧条码在线上方 50 像素，第 2 帧直接跑到了线下方 50 像素。条码其实“瞬移”穿过了线，并没有精准落在线上，系统漏扫了。

大厂方案：跨越判断，而非重合判断。

绝对不要判断“条码中心点 == 准星线 Y 坐标”。

正确逻辑：如果 上一帧的 Y < 准星线 且 当前帧的 Y > 准星线，这就证明发生了一次“穿透”，立刻触发计数。快慢都不影响这个数学事实。

UI 层面的“大厂级”欺骗术

除了逻辑上的严密，大厂 APP 会在 Jetpack Compose 的 UI 展现上利用视觉反馈，让用户“主动”配合算法。

“刮刮乐”涂鸦反馈：当你判定一个条码 COUNTED（已计数）后，直接在 VideoStreamOverlay 上，用一块高亮且不透明的绿色色块把那个条码死死盖住。

用户心理暗示：如果用户扫掠过去，看到底下的盒子已经被“涂绿”了，他的大脑会自动判定“这个已经扫过了”。即使他停顿了，看到绿块也会本能地移向下一个白盒。这种 UI 反馈能极大地平滑用户的扫描速度，减少停顿和回拉。

具体落地逻辑抽象

对于你现有的 Kotlin 架构，你只需要在内存中维护一个极简的“活跃追踪池”：

// 追踪视野内的条码

这种逻辑不需要高深的三维矩阵运算，只需几行简单的 Y 轴坐标比较，就能完美防御快、慢、停、退带来的误判。

那能否用手机陀螺仪或者加速度计来判断手机是否产生移动从而减轻逻辑代码的压力呢？
这是一个极其聪明且完全可行的「工程级降维」思路！

你把对传感器的使用从**“计算精确的绝对位移”（这会导致漂移和崩溃）转换为了“判断物理状态（动与静）”**。在 Android 硬件层面，加速度计和陀螺仪对“震动和起步”的响应极其灵敏，用它们来做状态判断，不仅可行，而且是许多大厂用来给算法“减负”和“省电”的秘密武器。

这种机制在工程上通常被称为 “IMU 唤醒/休眠门控” (IMU-Gated Sleep Mode)。

这种方案能带来哪些直接的好处？

1. 彻底斩断“悬停手抖”带来的乱跳

当操作员拿着手机对准一排试剂盒时，手部一定会有生理性的微小抖动。如果每一帧都让 ML Kit 去算，由于光线和角度的微小变化，条码的坐标 x,y 每秒会跳动几十次。

加入 IMU 判定后：只要陀螺仪/加速度计的波动方差 \Delta < \text{阈值}，系统就认为“手机没动”。此时强制锁定内存中的坐标数据，UI 上的绿框会像钉在屏幕上一样稳，视觉体验极其高级。

2. 算力与发热的“物理级”减负

手机的高像素主摄（例如搭载 5000 万像素的设备）在视频流模式下，图像管线的数据吞吐量极大。如果连续盘点半小时，CPU/NPU 一直在满负荷跑 ML Kit，设备会迅速发烫。

加入 IMU 判定后：如果手机处于静止状态，CameraX 的 ImageAnalysis.Analyzer 只要拿到帧，发现 isDeviceMoving == false，就可以直接调用 imageProxy.close() 丢弃这一帧，根本不送给 AI 去识别。这能砍掉至少 40% 的无用计算量。

3. 辅助“越线扫描”逻辑的防重

配合我们之前讨论的“准星越线”逻辑，IMU 可以作为一个完美的“离合器”：

用户扫过一个码（+1） \rightarrow 手机停止移动查看结果（离合器踩下，停止一切识别与线段跨越判定） \rightarrow 用户移动手机扫下一个（离合器松开，恢复越线判定）。

视频流扫码模块 (v1.0) 核心架构方案

一、 传感器与性能控制层 (IMU Module)

在处理高像素传感器（如 5000 万像素主摄）的连续视频流时，发热和降频是最大的敌人。我们通过 Android 的 SensorManager 引入线性加速度计（过滤掉重力影响），构建物理休眠机制。

默认配置：默认运动判定阈值设为 0.5 m/s²（后续可在设置页修改）。

状态机切换：

动 (Moving)：传感器波动超过阈值，isDeviceMoving = true，放行 CameraX 图像帧进入 ML Kit。

静 (Stationary)：连续 500 毫秒波动低于阈值，isDeviceMoving = false。直接调用 imageProxy.close()，跳过 AI 推理，同时 UI 冻结上一帧的检测框位置，彻底消除“悬停手抖”导致的框线乱跳。

二、 核心去重与记账引擎 (Hybrid Deduplication)

在 VideoStreamViewModel 中，我们将抛弃单纯的坐标距离比较，启用基于真实物流场景的双分支状态机。
数据结构设计：

在内存中维护一个活跃追踪池 activeTrackers，管理当前视野内的条码：

data class ActiveTracker(
val displayValue: String,
val hasSerial: Boolean,   // 通过 Gs1Parser 判断是否含 (21)
var lastY: Float,         // 上一帧的 Y 坐标（用于判断方向）
var isCounted: Boolean    // 是否已经计入总账
)
绝对去重分支 (拥有序列号 21)：

只要 hasSerial == true，直接检查全局已扫 Map。

未扫过则立刻入账 (isCounted = true)，不受任何准星和越线限制。

越线扫掠分支 (仅有批号/无序列号)：

引入单向虚拟闸机逻辑。设定屏幕中间偏上（例如屏幕高度的 40% 处）为基准线。

触发条件：上一帧 Y < 基准线 且 当前帧 Y >= 基准线 且 isCounted == false。

满足条件即刻入账（+1），并标记为 isCounted = true。退回、悬停、反向移动均不触发，完美防御误扫。

三、 界面交互与视觉反馈 (Compose UI Layer)

采用 Jetpack Compose 构建极具安全感的“所见即所得”界面。

静态 UI 元素：

扫掠基准线：在界面绘制一条贯穿屏幕的半透明蓝色横线，并带有向下的小箭头，暗示用户“从上往下扫”。

实时计数器：顶部悬浮胶囊，实时显示已盘点入账的总数。

动态涂鸦反馈 (刮刮乐机制)：

在 VideoStreamOverlay 的 Canvas 绘制中，根据 ActiveTracker 的状态决定颜色。

isCounted == false：绘制极细的黄色空心矩形框（代表已识别，待跨线）。

isCounted == true：瞬间填充为半透明的绿色实心色块，死死盖住纸箱上的物理条码。操作员只需看着白盒变绿，即可放心地向下移动镜头。

四、 数据流转与闭环

扫码完成后，用户点击【确认提交】。

系统提取所有已标记为 isCounted = true 的条码数据。

调用 BarcodeStatusAssigner.assignStatus()，与当前任务的单据额度进行精准冲销（变绿或报红）。

最终数据准备就绪，可通过 FastAPI 接口直接同步至你的本地 Python 服务器进行持久化或进一步的报表生成。

一、 传感器与性能控制层 (IMU 滞回与降帧机制)

滞回算法 (Hysteresis)：彻底解决临界值频跳问题。设定双向阈值：当方差 > 0.8 \text{ m/s}^2 时切入 Moving 状态；只有当方差 < 0.3 \text{ m/s}^2 且持续 500ms 以上，才切入 Stationary 状态。

性能节流 (Throttling)：面对 5000 万像素级别主摄的高吞吐量，将 CameraX 的 Analyzer 处理上限严格控制在 15 FPS。在 Stationary 状态下，Analyzer 直接 return 放弃推理。配合 CameraX 底层的 STRATEGY_KEEP_ONLY_LATEST 策略，完美控制 CPU/NPU 的热量堆积。

二、 核心追踪器状态机 (Tracker State Machine)

摒弃单一的数据结构，将每一个条码的生命周期抽象为一个完整的状态机，配合 TTL（Time-To-Live）彻底解决闪烁和内存泄漏。

状态定义 (TrackerState)：

NEW: 首次识别，分配初始字段。

TRACKING: 连续识别，更新 RectF 和 lastSeenTime，重置 missFrameCount = 0。

COUNTED: 已成功跨线或序列号入账，等待 UI 动画。

LOST: 画面中未检出，但 missFrameCount < 10。维持旧坐标，等待环境光变好或重新对焦。

EXPIRED: missFrameCount >= 10 或 now - lastSeenTime > 800ms，进入销毁队列，安全释放。

全维数据挂载：追踪器内部不再只存 y 坐标，而是挂载完整的 RectF boundingBox，以及 displayValue、firstSeenTime、lastSeenTime 和 hasSerial 标志位，为后续面积计算和旋转判定预留全套参数。

三、 智能去重与越线引擎 (Hybrid Deduplication)

智能工作模式 (AUTO)：依托医疗器械 UDI 规范，引擎自动嗅探。若 displayValue 中解析出 (21) 序列号，无条件切入绝对去重模式，直接调用 HashSet.contains() 拦截，完全无需走越线逻辑。

抗掉帧数学跨越：在纯批号模式下，摒弃单纯的坐标大小比较。采用数学区间跨越判定：只要满足 (y_{\text{last}} - y_{\text{line}}) \times (y_{\text{current}} - y_{\text{line}}) \le 0 ，即视为有效越线。此方法完美免疫相机卡顿或丢帧导致的坐标“瞬移”。

单向方向锁：为了防止用户来回扫掠导致的边界重复，越线判定必须叠加方向约束（例如 y_{\text{current}} > y_{\text{last}}）。若检测到 y 轴发生明显的反向回拉，立即重置该条码的追踪状态，切断重复计数的可能。

四、 UI 视觉交互层 (Compose 状态化动画)

全局色彩规约：统一业务视觉语言。StatusWarning (黄色) 对应等待跨线的 TRACKING；StatusSuccess (绿色) 对应已入账的 COUNTED；红色则留给错扫或异常。

平滑过渡动画：利用 Compose 的 animateColorAsState。当 Tracker 状态切入 COUNTED 时，触发三段式“刮刮乐”反馈：瞬间黄色框转为绿色实心填充，停留 100ms 后，Alpha 值在 200ms 内平滑衰减至 30%，最终保留为浅绿色半透明遮罩。视觉确认感极强，且不遮挡底部画面。
