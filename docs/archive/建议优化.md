InventoryMaster AI 集成优化建议

文档目的

在现有《AI 集成方案》的基础上，对架构设计、可扩展性、用户体验和医疗器械仓储业务场景进行优化，避免后期出现架构耦合、维护困难和功能扩展受限的问题。

---

一、总体建议

当前方案已经具备：

- 统一 "AiService" 接口
- 多 Provider 支持
- Tool Calling 机制
- 云端与本地模型分层
- 分阶段实施路线

整体设计已经达到较高水平。

建议进一步向「垂直领域 AI Agent」方向演进，而不是仅实现聊天功能。

推荐目标：

扫描UDI
    ↓
AI自动识别产品
    ↓
自动关联历史批号
    ↓
发现异常数量
    ↓
推测异常原因
    ↓
生成盘点报告
    ↓
一键提交ERP

最终定位：

InventoryMaster 医疗器械仓储智能助手（Inventory AI Agent）

---

二、增加 Agent 层

当前架构

ChatViewModel
        ↓
    AiService
        ↓
Repository

问题：

- ViewModel 会承担大量 AI 逻辑
- 后续增加 OCR、异常分析、多轮对话时容易失控
- 代码职责不清晰

---

建议架构

ChatViewModel
        ↓
      AiAgent
        ↓
   ToolExecutor
        ↓
Repository
        ↓
    AiService

建议目录：

ai/
├── agent/
├── tools/
├── provider/
├── prompt/
├── memory/
├── model/
└── executor/

示例：

interface AiAgent {
    suspend fun chat(message: String): Flow<ChatEvent>
}

优点：

- ViewModel 保持轻量
- AI 能力完全独立
- 后续扩展成本低

---

三、增加 ToolExecutor 和 ToolRegistry

当前方案

AI
 ↓
Repository.searchProducts()

AI
 ↓
Repository.countInventory()

问题：

后期工具数量增加后：

when(toolName) {
    "search_products" -> ...
    "count_inventory" -> ...
    "search_records" -> ...
}

会逐渐演变为维护困难的大型分支代码。

---

建议设计

工具接口

interface AiTool {
    val name: String

    suspend fun execute(
        arguments: JsonObject
    ): String
}

工具注册中心

object ToolRegistry {
    fun register(tool: AiTool)
    fun get(name: String): AiTool?
}

执行器

class ToolExecutor {
    suspend fun execute(
        toolName: String,
        arguments: JsonObject
    ): String
}

---

推荐工具目录

tools/
├── SearchProductsTool
├── SearchRecordsTool
├── CountInventoryTool
├── GetProductDetailTool
├── AnalyzeAbnormalTool
├── ImportExcelTool
├── ExportExcelTool
└── OpenSessionTool

优点：

- 插件化
- 易测试
- 易扩展
- 解耦 Repository

四、增加流式输出（Streaming）

问题

查询大量数据时：

查一下所有产品

可能等待数秒。

用户会误认为：

程序卡死
网络异常

---

建议

扩展接口：

interface AiService {

    suspend fun chat(...): AiResponse

    fun streamChat(...): Flow<StreamChunk>
}

---

UI 示例

AI：
正在查询库存……

找到 5230 条产品……

正在整理结果……

查询完成。

优点：

- 反馈及时
- 提升感知性能
- 更适合弱网环境

五、System Prompt 动态构建

当前方案

const val SYSTEM_PROMPT

问题：

Prompt 固定。

无法感知：

- 当前盘点单
- 当前筛选条件
- 当前产品
- 当前扫描模式

---

建议

PromptBuilder.build(
    session,
    user,
    tools
)

动态生成：

当前盘点任务：
XXX

当前记录数：
523

当前时间：
2026-06-16

当前筛选：
差异项

可用工具：
...

优点：

- Prompt 更准确
- Token 更节省
- AI 上下文更丰富

六、增加会话记忆（Conversation Memory）

问题

用户：

查一下注射器

AI：

找到3种注射器

用户：

第二个批号是多少？

AI 无法理解。

---

建议

data class ChatSession(
    val messages: MutableList<AiMessage>,
    val context: MutableMap<String, Any>
)

建议保存：

lastSearchProducts
lastSelectedProduct
lastInventorySession
lastFilterCondition

优点：

- 支持连续问答
- 支持引用历史结果
- 更接近真实助手体验

七、支持结构化响应

当前方式

找到3种注射器

只能显示文本。

---

建议

data class AiAnswer(
    val message: String,
    val actions: List<UiAction>
)

例如：

{
  "message":"找到3种注射器",
  "actions":[
    {
      "type":"OPEN_PRODUCT_LIST",
      "productKeys":[]
    }
  ]
}

UI：

找到3种注射器

[查看产品]

点击：

直接打开产品列表。

---

推荐动作类型

OPEN_PRODUCT_LIST
OPEN_RECORD_LIST
OPEN_PRODUCT_DETAIL
OPEN_SESSION
COPY_RESULT
EXPORT_REPORT

优点：

- AI 与界面联动
- 减少手工操作
- 更符合仓储业务流程

八、异常分析能力（高价值功能）

相比普通聊天：

查一下注射器库存

异常分析价值更高。

---

建议工具

analyze_inventory_abnormal()

返回：

发现12条异常：

一次性注射器
ERP：100
实盘：0

输液器
ERP：0
实盘：50

AI：

可能存在：

1. 漏盘
2. 串货
3. ERP历史数据未同步
4. 重复扫描

价值：

- 快速发现问题
- 辅助决策
- 减少人工分析时间

九、OCR 智能纠错

项目已经具备：

- CameraX
- ML Kit OCR
- UDI 解析
- 产品数据库

非常适合增加：

OCR → AI 修复

OCR：

69724598O00017

实际：

69724598000017

AI：

发现字符 O 与数字 0 混淆。

根据 GS1 编码规则，
推测正确 DI：

69724598000017

还可以：

- 自动修正批号
- 自动修正效期
- 自动识别生产日期格式
- 自动补全缺失字段

这是医疗器械场景非常实用的能力。

---

十、API Key 安全

当前：

DataStore 明文存储

建议：

EncryptedSharedPreferences

或者：

Jetpack Security Crypto

原因：

- adb 导出
- Root
- 日志泄露
- 备份恢复

都可能导致 Key 泄露。

十一、Provider 策略优化

当前：

QWEN
DEEPSEEK
GLM
ERNIE
LOCAL

建议：

Phase 1

仅支持：

QWEN
DEEPSEEK

原因：

Qwen

- Tool Calling 成熟
- OpenAI 协议兼容好
- 中文能力优秀

DeepSeek

- 成本低
- 推理能力强
- 部署简单

---

暂缓支持

GLM

协议偶有变化。

ERNIE

兼容层复杂。

LOCAL

模型下载、JNI、兼容性问题较多。

优先完成业务价值，再处理兼容问题。
