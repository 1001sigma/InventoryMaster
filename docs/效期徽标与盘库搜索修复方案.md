# 效期徽标与盘库搜索修复方案

> 2026-09-20 · 覆盖范围：Android 端（InventoryMaster）+ 服务端（D:\xz\inventory_server）
> 关联问题：① 盘库近效期/已过期徽标对服务端拉取的数据不显示；② 盘库搜索栏搜索能力与提示文案不符

---

## 1. 背景与根因

### 1.1 徽标不显示

同一条 `expiry_date`（Long）在两端有两种并存语义，且消费方各认一种：

| 写入方 | 存储值 | App 徽标判定 | Web 看板判定 |
|---|---|---|---|
| App 推送 / GS1 扫码 | YYYYMMDD（如 20261231） | ✅ 正常 | ❌ 显示"已过期约 2 万天" |
| 服务端 Excel 导入（真日期单元格） | 毫秒时间戳（13 位） | ❌ 无徽标 | ✅ 正常 |
| 服务端 Excel 导入（字符串单元格） | **导入时刻**（数据本身已错） | ❌ 无徽标 | ⚠️ 值错误 |

- 服务端写入：`templates/api/excel.py:271-282`——真日期单元格存 `int(ts*1000)`，字符串存"当前时刻"，只有纯数字单元格存对
- App 显示：`DateUtils.formatDateForDisplay`（`DateUtils.kt:31`）双格式兼容，所以**日期显示正常、掩盖了问题**
- App 徽标：`InventoryViewModel.parseExpiryDate`（`InventoryViewModel.kt:318`）只认 8 位/6 位 → 毫秒解析失败 → `NORMAL` → 无徽标
- Web 徽标：`detail.html:369` `expiryState()` 用 `expiryTs - Date.now()` 计算，只认毫秒
- AI 异常分析：`AnomalyDetector.kt:63-84` 自带第三套判定，遇毫秒记录会漏判过期且 `LocalDate.parse` 抛异常（文件内无 try/catch，整次分析失败）

### 1.2 搜索栏

- DAO 的 9 字段模糊查询 `searchRecordsByQuery`（`StockRecordDao.kt:58-75`）**全工程无调用方**；实际执行的 `getRecordsByKeyOrDiOrMat`（`StockRecordDao.kt:127-138`）只对组合键/DI/物料编码做**精确等值匹配** → 输入品名/厂家/库位/批号一律"未找到"
- 空查询 `= ''` 精确匹配 → 返回空列表；进入任务页 `selectSession` 清空后**无初始加载**，空态文案"暂无盘点记录"误导
- 门铃静默拉取（`silentDoorbellPull`）后**不重建** `searchResults`（一次性快照）；增删改都会重搜，这是唯一漏网路径

## 3. 改动一：客户端效期解析统一（P0）

**原则：毫秒判定复用 `DateUtils.isUnixTimestamp` 的现成区间（2000–2100 年），它与 8 位 YYYYMMDD（约 2×10⁷）数值区间无重叠，不会误判；禁止自造阈值。**

### 3.1 `DateUtils.kt` 新增唯一入口

```kotlin
/** 效期/生产日期 Long → LocalDate。
 *  兼容三种形态：毫秒时间戳（服务端 Excel 导入历史数据）、yyyyMMdd、yyMMdd。
 *  解析失败返回 null（调用方按 NORMAL 处理）。 */
fun toLocalDate(dateLong: Long): LocalDate? {
    if (isUnixTimestamp(dateLong)) {
        return try {
            Instant.ofEpochMilli(dateLong).atZone(ZoneId.systemDefault()).toLocalDate()
        } catch (e: Exception) { null }
    }
    val s = dateLong.toString()
    return try {
        when (s.length) {
            8 -> LocalDate.parse(s, DateTimeFormatter.ofPattern("yyyyMMdd"))
            6 -> LocalDate.parse(s, DateTimeFormatter.ofPattern("yyMMdd"))
            else -> null
        }
    } catch (e: Exception) { null }
}
```

### 3.2 `InventoryViewModel.mapToUiModels`（280-307 行）切换到新入口

- `parseExpiryDate(expiryStr, ...)` 两处调用改为 `DateUtils.toLocalDate(record.expiryDate)` / `toLocalDate(productionDate)`
- 旧 `parseExpiryDate`（318-328 行）删除（无其他调用方）
- 徽标三规则（<0 过期 / ≤阈值天数 近效期 / 剩余<总效期25% 近效期）逻辑不变

### 3.3 可选项：GS1 日=00（日未知）

AI(17) 允许 DD=00（如 20261200），当前 `LocalDate.parse` 失败 → 无徽标。按 GS1 惯例"日未知=当月最后一天"处理：`toLocalDate` 中 8 位且日为 00 时回退到 `YearMonth.atEndOfMonth()`。**默认做**，影响仅限此前完全不显示徽标的记录。

**影响面（已核实无副作用）**：显示路径本就双格式；同步冲突检测只比 qty/actual/remarks/operator；推送、GS1 扫码、batchscanner、Excel/PDF 导出、手机端 Excel 导入均不经过此函数。

## 5. 改动三：服务端归一化 + Web 双格式（P1，成对上线）

> ⚠️ 只改 excel.py 不改 detail.html，会把"新导入记录在 web 上显示已过期 2 万天"——两处必须同一批部署。

> **实施补充（2026-09-24）**：排查发现服务端有**两条** Excel 导入路径，均存毫秒——legacy 路径 `templates/api/excel.py` 与模板/映射式路径 `templates/core/excel_utils.py::execute_import`（经 `_parse_date_to_ms`）。实施时已将后者一并替换：`core/excel_utils.py` 新增统一归一化函数 `parse_date_to_yyyymmdd()`（替换并删除 `_parse_date_to_ms`），legacy 路径导入复用同一函数，行为经冒烟测试验证（真日期/各字符串格式/数字/日=00/垃圾值/None 全覆盖）。两条路径同时补齐 `production_date` 写入。

### 5.1 `templates/api/excel.py`（271-282 行）重写日期转换

统一产出 YYYYMMDD int（与 App 实体注释"效期 (17)"语义对齐）：

```python
raw_date = row.get("expiryDate", 0)
expiry_val = 0
try:
    if pd.notnull(raw_date):
        if hasattr(raw_date, "timestamp"):            # Excel 真日期单元格
            expiry_val = int(raw_date.strftime("%Y%m%d"))
        elif isinstance(raw_date, str):               # 字符串：尽力解析，失败置 0
            parsed = pd.to_datetime(raw_date, errors="coerce")
            expiry_val = int(parsed.strftime("%Y%m%d")) if pd.notna(parsed) else 0
        else:                                         # 纯数字：校验 6/8 位且年份合理
            n = int(raw_date)
            expiry_val = n if (len(str(n)) in (6, 8) and 19000000 <= n <= 21001231) else 0
except Exception:
    expiry_val = 0
```

`production_date` 列按同样规则一并支持（当前完全没写入，导致 App 端"剩余<25%"规则对这些记录永不触发）；Excel 表头映射（202 行附近）补"生产日期"别名。

### 5.2 `templates/detail.html` 效期判定双格式

`expiryState()`（369 行）改为与 `DateUtils` 同款阈值判定：

```js
function expiryDateToMs(v) {
    if (v > 946684800000 && v < 4102444800000) return v;          // 毫秒（历史数据）
    var s = String(v);
    if (s.length === 8) {                                          // YYYYMMDD
        var y = +s.slice(0,4), m = +s.slice(4,6), d = +s.slice(6,8);
        if (m >= 1 && m <= 12 && d >= 1 && d <= 31) return new Date(y, m-1, d).getTime();
    }
    return null;
}
// expiryState 内：var ms = expiryDateToMs(expiryTs); if (!ms) return null; 其余天数逻辑不变
```

排查统一走该函数的调用点：302 / 378 / 408 / 423 / 460 行（含 R7 近效期筛选），确保没有第二份日期计算逻辑。
